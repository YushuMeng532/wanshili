# 前端实现中的需求与 Spec 问题汇总

日期：2026-11-19 · 对照工作台 V0.4 的 [PRD](modules/01-calendar/prd.md)、[Dev Spec](modules/01-calendar/dev-spec.md)、[页面设计](modules/01-calendar/page-design.md)。

[打开独立前端](../app.html) · [返回工作台](../index.html)

## 1. 交付范围混用了“原型、前端演示、MVP”

PRD第1节把每日确认、统计和本地保存列为后续；第5节详细规定统计，第6节又称真实保存待实现。Spec同时列出Repository等产品契约与原型文件，难以直接判断当前交付应做到哪一步。

影响：设计、开发、验收容易各自采用不同的“完成”标准，出现能点通却不能刷新保存，或静态统计被理解为真实统计的情况。

建议：每一版先列交付范围，再分别标识“静态展示、交互可用、本地数据可用、服务已接入”。本次前端实现本地事项和每日确认、真实日期去重统计；AI服务、农历、假调休与系列历史处理保留明确边界。

## 2. 日历里的“事项标记”没有实例口径

PRD要求展示日期对应的事项，但未明确倒数日是否从创建日起每天出现、正计时是否即使不循环也每天出现，以及标记是否意味着已完成。

影响：相同数据会生成不同的日历、当天列表和“未记录”范围。

建议改写：“日历标记由日期与循环生成的计划实例决定；仅一次只在指定日出现。标记不代表已发生。正计时数字属于展示指标，不改变计划实例。”本次按这个口径生成计划，并将确认状态单独显示。

## 3. 起始日、持续天数与累计第几天不够清楚

PRD把第0/1天列为待确认；持续天数是否包含开始日，以及循环事项是按自然日截止还是出现次数截止，尚未定义。

影响：持续30天可能多生成一天，也可能被实现为30次循环；不同位置的累计数字可能相差1。

建议分别定义“累计展示天数”“有效日期区间”“计划出现次数”。本次不显示有争议的累计第几天；持续天数子层明确开始日计入自然日区间。这是演示采用的暂定口径，需要确认后写入PRD。

## 4. 循环子层的字段与取消行为不完整

Spec列出monthDay、yearMonth、yearDay，但没有定义初值、编辑回填、取消时是否提交，或周循环至少选择几个星期。

影响：子层取消也可能悄悄改值；按开始日期回填可能覆盖用户之前选择的循环日期。

建议：子层持有临时值，点“完成”才提交给主表单；关闭保持原值。每周至少选一天，按周一至周日排序，月/年日期独立回填。本次按此实现，并保留主表单的名称和备注。

## 5. 缺少月日与闰日不能只写“待确认”

PRD没有规定每月31日遇到2月、每年2月29日遇到平年时的结果。

影响：自动改为月末会改变用户意图，直接跳过又可能让用户误以为事项丢失。

建议在产品确认“跳过 / 月末 / 提醒用户选择”之一，并配套可见提示与测试日期。本次不代算，月/年循环配置中明确说明缺少日期时不生成；这仍属于暂定演示行为。

## 6. 假调休契约缺少数据交付责任

Spec定义HolidayCalendar和HOLIDAY_DATA_MISSING，但没有提供年份、来源、版本、更新方式和失败展示。

影响：“工作日”容易被错误实现为周一至周五，形成确定性的漏提醒与误提醒。

建议：补充可用年份、数据文件或接口、来源、年度更新责任，以及缺失时“禁止保存并返回选择”的交互。本次工作日选项显示数据未接入，保留表单和原循环，不使用周一至周五代替。

## 7. 农历生日缺少可实施的数据模型

Event只有date与calendarType，PRD又要求保留原历法日期。仅用YYYY-MM-DD无法清晰表达农历月日、闰月标识及每年换算后的公历日期。

影响：同一个字段会被混用为原生日、农历日期和本年度换算结果；遇闰月无法稳定重算。

建议增加birthdaySource={calendar,month,day,isLeapMonth,year?}，将换算得到的公历日期作为派生实例；确定转换库、支持年份及闰月规则。本次保留农历入口并说明未接入，阻止将未换算数据当成公历保存。

## 8. 系列操作候选项还不能直接作为开发规则

PRD的“仅这一次 / 这次及之后”“仅这一次 / 整个系列”是候选，同时注明历史处理待确认。Spec给出例外对象，却没有系列分段、后续记录归属或修改生效边界。

影响：实现“这次及之后”可能重写历史配置；“整个系列”可能连同真实记录一起删除，进而改变月度统计。

建议先确定边界日期是否包含当前日、既有DailyRecord是否保留、变更类型如何归类、删除是否可恢复，再定义系列分段ID和迁移规则。本次仅实现单次覆盖与单次计划取消；后续/整个系列操作明确不可用。

## 9. “删除事项”和“删除确认记录”需要拆开

PRD既要求删除事项更新列表，又要求删除原记录后统计重算，但没有区分删除计划与清除实际确认。

影响：用户取消一个计划可能意外抹掉已发生事实；开发无法判断统计变化是否属于缺陷。

建议：分别使用“取消当天计划”“删除系列”“清除当天确认记录”，写出各自影响。此次循环单次删除只取消计划，保留真实确认；非循环事项删除会在确认文案中说明移除当天确认。两种口径需要产品统一后再扩展。

## 10. 记录统计缺少历史归类与孤立记录约定

Spec只写DailyRecord的eventId，没有说明事项改类型、删系列后历史记录应按当时类型还是当前类型归类，也没有说明事件已删除但记录保留时的统计明细入口。

影响：同一份历史记录的类型天数可能随事项配置改变；合计有天数，列表却找不到原事项。

建议记录确认时的类型快照，定义归档事项和历史明细访问；若允许重分类，应成为单独的显式操作。本次确认记录保存当时类型，统计按occurred日期并集计算，不把计划、跨度和倒数直接计入。

## 11. AI“建议”和开关混在同一交付说明中

文档说明分析范围与确认写入，但没有漏记识别阈值、触发频率、询问位置、建议来源与可撤销规则。

影响：界面可能给出没有数据依据的提醒，用户也无法判断开关是否已经调用外部服务。

建议把“偏好配置”和“分析服务”分为两个需求，补齐触发样例、负例和确认后冲突处理。本次只保存全局/单项偏好，不生成AI结果。

## 12. 本地保存的失败与恢复方案需要补足

Spec要求读取失败保留旧数据，但未给出schema升级、坏数据恢复、空间不足与多标签页竞争的处理。

影响：普通JSON解析后覆盖写入可能丢数据；两个标签页可能互相覆盖。

建议定义版本迁移、原文备份、只读恢复态、写入失败重试和跨标签页冲突检测。本次先写入成功再更新界面；失败保留草稿与原数据，读取异常时显示保存不可用。多标签页冲突和迁移仍需后续补齐。

## 建议先确认的顺序

先锁定本版交付范围和日历实例口径，再确认系列历史与删除语义；随后补齐农历、假调休和特殊月日规则。AI服务另立需求，避免阻塞已明确的记录流程。
