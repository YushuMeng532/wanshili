# 万事历｜竞品发现与功能取舍
2026-11-18 · 作品集摘要

## 1. 调研目标

明确日历基础能力，选择适合轻量记录的交互，为“每天记录—月末汇总天数”确定功能优先级。

## 2. 竞品选择及能力

| 竞品与选择理由 | 官方已描述能力 | 对万事历的启发 |
| --- | --- | --- |
| [Google Calendar](https://support.google.com/calendar/answer/37115)：通用日历 | 按周期重复事件 | 类型与循环分开，减少反复新建 |
| [TimeTree](https://timetreeapp.com/intl/en)：多事项组织 | 多日历、筛选、聚合查看 | 先保证同日多项可读，暂缓共享 |
| [TickTick](https://help.ticktick.com/articles/7055781805944733696)：日历结合习惯 | 打卡概览、月度打卡表，部分有平台条件 | 月度统计已有成熟先例；重点定义口径与核对路径 |
| [Daylio](https://daylio.net/)：快速日常记录 | 活动选择、日历、月年统计 | 名称复用、当天确认、备注选填 |
| [Habitify](https://habitify.me/)：持续记录 | 日历历史、连续记录与进展 | 区分持续跨度与本月实际发生天数 |
| [YouLoft万年历](https://www.51wnl.com/)：本地化日历 | 农历、节日假期、提醒与待办 | 支持生日历法与工作日假调休规则 |

## 3. 核心任务分析

| 用户任务 | 竞品能力带来的判断 | 产品决策 |
| --- | --- | --- |
| 新建重复事项 | 周期设置已是基础能力 | 带入选中日期，循环单独设置 |
| 同日记录多个活动 | 列表组织和活动选择能减少重复输入 | 当天多项列表、快速确认发生状态 |
| 月末查看发生几天 | 习惯及日志产品已有统计基础 | 每事项及类型按实际日期去重，合计可点开 |
| 修正过去记录 | 合计需要可追溯 | 从统计定位原记录，修改后重算 |

## 4. 从竞品到具体功能

| 成熟能力 | 用户需要 | 万事历功能 | 优先级 |
| --- | --- | --- | --- |
| 月历与重复 | 快速安排每日事项 | 同日多项、三种类型、循环 | 本期 |
| 活动选择与日志 | 区分计划与实际发生 | 已发生/未发生/未记录 | 本期 |
| 月度打卡与统计 | 月底算清每类事项多少天 | 每事项及类型天数、日期明细、修正同步 | 本期重点 |
| 农历与假期 | 生日与工作日安排准确 | 农历生日、中国假调休 | 本期，边界规则待定 |
| 历史回顾 | 检查遗漏 | 先列待确认日期，再评估AI询问 | AI后置 |
| 共享协作 | 多人协调 | 首版聚焦个人，暂缓共享 | 后续评估 |

## 5. 产品设计结论

基础采用成熟月历和循环，首版价值集中在“轻量记录 + 月末天数核对”。流程：选择日期 → 创建事项 → 确认发生 → 月度合计 → 日期明细 → 修正。

四类核心页面：日历主页、事项创建、事项详情、月度统计。优先完成记录、汇总和保存，再验证AI建议。

## 6. 待验证点

本轮依据官方功能说明及既有调研，尚未完成统一设备逐项实测。月度统计并非竞品空白，差异化假设在于同一日历中完成多类型记录及可追溯的天数核对。需实测创建成本、循环作用范围、统计维度和持续记录意愿；不填写虚构点击数或体验耗时。
